# База знаний: где живёт, из чего состоит, как подтверждается

База знаний — **источник истины для ответов бота**: в промпт уходят только факты из карточек.
Сайт администрации базой **не является** — он один из первоисточников, по которому факт сверяют
при написании карточки. В рантайме бот за фактами в интернет не ходит.

## Где что лежит

| Слой | Место | Правило |
| :-- | :-- | :-- |
| Контент — карточки | `knowledge/faq/*.md` (этот репозиторий) | единственный источник истины; один файл = одна карточка; правки только через PR |
| Первоисточники | `knowledge/sources/` — административные регламенты, постановления, распоряжения | документ — доказательство факта, а не то, что бот читает; факт переносим в карточку |
| Индекс поиска | собирается из карточек при сборке (Шаг 3: SQLite FTS5, далее — векторы) | руками не правится |
| Состояние (очередь, лимиты, id сообщений) | SQLite на отдельном томе CT104, вне образа | переживает пересборку контейнера |
| Бэкап | git remote + vzdump на pve1 | восстановление проверяем, а не «настроили и забыли» |

Почему git, а не вики/Notion: версии и дифы по каждой карточке, ревью, откат — и никакого внешнего
сервиса, что соответствует требованию «только РФ в рантайме».

## Структура

- `knowledge/README.md` — этот файл, правила;
- `knowledge/sources/` — первоисточники (нормативные документы);
- `knowledge/faq/` — карточки, один файл = одна карточка; `_template.md` — шаблон.

Папка `faq/` — отдельная, чтобы `Path('knowledge').glob('*.md')` не цеплял README.

## Формат карточки

Шаблон — `faq/_template.md`. Поля:

- **заголовок-вопрос** — как вопрос задаёт житель;
- **`ключевые слова:`** — синонимы и разговорные формы (в том числе `приём`/`прием`, с «ё» и без);
- **факты** — короткими абзацами; телефоны, адреса, сроки — точно как в источнике;
- **`источник:`** — откуда факт проверен; строк может быть несколько (страница, документ, объявление);
- **`подтвердил:`** — кто подтвердил и когда (управление/отдел, ФИО, дата) — для фактов, которых нет в нормативном документе;
- **`проверено:`** — дата последней сверки с источником;
- **`статус:`** — `подтверждено` | `по-источнику` | `черновик`.

`по-источнику` честно означает «взято с сайта, владельцем не подтверждено». Таких карточек должно
становиться меньше, а не больше: это видимая метрика надёжности базы.

## Иерархия источников

1. **Нормативный документ** — постановление, административный регламент, распоряжение. Высший приоритет.
2. **Страница сайта** администрации — если нормативки нет.
3. **Картинка, объявление, скан** — только подсказка: факт из картинки поиском не найдётся, его
   обязательно переносим в текст карточки.

Проверено на практике (карточка «режим работы»):

- **Устаревшее — не источник.** Свежесть документа проверяем по метаданным файла
  (`unzip -p файл.docx docProps/core.xml` для `.docx`), а не по дате публикации на сайте.
- **Два URL ≠ два источника.** Одна и та же страница по внутреннему номеру и по человекочитаемому
  пути (`/node/183` = `/content/obrashcheniya-grazhdan`) — это одно подтверждение, а не два.
- **Часы приёма органа, отдела или управления не выдаём за режим работы администрации** — всегда
  называем субъекта (кто именно так принимает).
- **Противоречие в источнике** — вопрос владельцу контента, а не молчаливый «выбор по вкусу».

## Что в базу не берём

- **Динамику** (отключения, погода, новости, предупреждения) — это инструменты Шага 4: в карточке
  она устареет за день.
- **Чужую зону** (медицина, полиция, суды, Соцфонд) — только как «куда обратиться», с честной
  формулировкой «это не наша услуга».
- **Персональные данные** и всё, что требует доступа к обращению конкретного человека (152-ФЗ, Шаг 5.1).

## Актуализация

- **Владелец базы** — сотрудник администрации: подтверждает факты и сообщает об изменениях. Сверка —
  раз в квартал и при каждом изменении регламента.
- **Вотчдог источника:** cron следит за хешем страниц и файлов на сайте администрации; источник
  изменился → задача на сверку карточки (та же механика, что у мониторинга сайтов).
- Правка карточки — через PR: видно, что именно поменяли и на каком основании.

## Процесс правки

1. Найти факт в первоисточнике (иерархия выше); если факта в нормативке нет — получить подтверждение владельца.
2. Правка карточки в ветке → PR → ревью → squash-merge.
3. В карточке обновить `проверено:` (и `статус:`/`подтвердил:` при смене основания).
4. Прогнать `evals/` (Шаг 6): изменение ответа — это регресс-тест качества.
